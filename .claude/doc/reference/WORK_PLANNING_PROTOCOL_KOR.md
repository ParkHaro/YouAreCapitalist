# 작업 계획 프로토콜

[🇬🇧 English Version](./WORK_PLANNING_PROTOCOL.md)

## 📍 네비게이션

[↩️ 레퍼런스로 돌아가기](./INDEX_KOR.md) | [📚 문서 인덱스](../INDEX_KOR.md) | [🏠 홈](../../../CLAUDE_KOR.md)

## 🚨 필수 프로토콜

**모든 개발 작업을 시작하기 전에 이 계획 프로토콜을 반드시 따라야 합니다.**

## 1. 사전 작업 상담 단계 (15-20분)

### 1.1 문서 안내 시스템

#### **1단계: 필수 문서 확인**
작업 논의 전, 관련 문서를 안내합니다:

```yaml
필수 읽기 확인:
  도메인 지식: 
    파일: .claude/doc/reference/DOMAIN_KNOWLEDGE_KOR.md
    상태: [✅ 읽음 / ❌ 읽어야 함]
    시간: 10-15분
  
  관련 아키텍처:
    파일: [관련 아키텍처 문서 목록]
    상태: [✅ 읽음 / ❌ 읽어야 함]
    시간: 문서당 5-10분

  게임 디자인 컨텍스트:
    파일: [관련 게임 디자인 문서 목록]  
    상태: [✅ 읽음 / ❌ 읽어야 함]
    시간: 범위에 따라 가변
```

#### **2단계: 누락된 문서 평가**
필수 문서가 누락된 경우:
1. **격차 식별**: "이 작업에는 [시스템 디자인] 문서가 필요합니다"
2. **필요성 평가**: "[이유] 때문에 이것이 중요합니다"
3. **생성 제안**: "먼저 이 문서를 만들어야 할까요?"
4. **시간 추정**: "적절히 문서화하는 데 대략 [시간]이 소요됩니다"

### 1.2 대화형 요구사항 수집

#### **필수 질문 체크리스트**
```yaml
범위 및 규모:
  - [ ] 이 작업의 최종 목표는 무엇인가?
  - [ ] 몇 개의 엔티티가 영향을 받을까? (>1000개 = ECS 필수)
  - [ ] 성능상 중요한가? (핫 패스 분석)
  - [ ] 성공 기준은 무엇인가?

기술적 제약사항:
  - [ ] UI 통합이 필요한가?
  - [ ] 기존 코드에 대한 의존성은?
  - [ ] Unity 버전 제약사항이 있나?
  - [ ] 모바일/PC 플랫폼 고려사항?

일정 및 리소스:
  - [ ] 선호하는 일정은?
  - [ ] 차단하는 의존성이 있나?
  - [ ] 더 작은 작업으로 나눌 수 있나?
  - [ ] 위험 허용도는?
```

#### **프로젝트별 제약사항**
```yaml
Unity 기술 스택:
  - 엔진: Unity 6000.2.0f1
  - 아키텍처: Unity DOTS (ECS)
  - 성능 목표: 100,000+ 엔티티 @ 60fps
  - 플랫폼: 모바일/PC 크로스 플랫폼

YouAreCapitalist 게임 제약사항:
  - 데이터 중심 시뮬레이션 (비주얼 게임 아님)
  - 3계층 아키텍처 (ECS/브리지/UI)
  - 자동화 시스템 통합
  - 경제 시뮬레이션 정확성
```

## 2. 작업 분해 구조 (WBS)

### 2.1 작업 계층 정의
```yaml
에픽 (1-2주):
  - 대규모 기능 구현
  - 시스템 아키텍처 변경
  - 주요 리팩토링 이니셔티브
  - 예시: "완전한 인구 시뮬레이션 시스템 구현"

스토리 (2-3일):
  - 구현 가능한 기능 단위
  - 테스트 가능한 컴포넌트
  - 명확한 승인 기준
  - 예시: "기본 AI를 가진 PopulationBehaviorSystem 생성"

작업 (2-4시간):
  - 구체적인 구현 작업
  - 단일 책임 집중
  - 측정 가능한 완성도
  - 예시: "PopulationData ECS 컴포넌트 구현"

하위 작업 (30분 - 2시간):
  - 구체적인 세부 단계
  - 더 이상의 분해 불필요
  - 즉시 실행 가능한 작업
  - 예시: "PopulationJob에 Burst 컴파일 추가"
```

### 2.2 우선순위 매트릭스 프레임워크
```yaml
우선순위 레벨:
  P0 - 치명적 (즉시):
    - 다른 작업 차단
    - 성능/안정성 이슈
    - 보안 취약점
  
  P1 - 높음 (이번 스프린트):
    - 중요한 기능
    - 아키텍처 개선
    - 사용자 대면 기능
  
  P2 - 보통 (다음 스프린트):
    - 있으면 좋은 기능
    - 코드 품질 개선
    - 비중요 최적화
  
  P3 - 낮음 (백로그):
    - 미래 개선사항
    - 실험적 기능
    - 문서 업데이트
```

### 2.3 의존성 매핑
```yaml
의존성 유형:
  기술적:
    - 코드 의존성 (Y 전에 X를 구현해야 함)
    - 시스템 의존성 (UI 브리지 전에 ECS)
    - 외부 의존성 (Unity 패키지)
  
  지식:
    - 문서 의존성 (코딩 전에 명세 필요)
    - 결정 의존성 (아키텍처 결정 필요)
    - 리뷰 의존성 (전문가 검증 필요)
  
  리소스:
    - 시간 의존성 (순서 제약사항)
    - 도구 의존성 (프로파일러, 테스팅 도구)
    - 환경 의존성 (개발 설정)
```

## 3. 협력적 계획 세션

### 3.1 대화 프레임워크

#### **세션 시작 대화**
```
어시스턴트: "[작업 설명]을 원하시는군요. 코딩을 시작하기 전에 필요한 모든 것이 있는지 확인해봅시다:

1. 📚 도메인 지식 문서를 검토하셨나요? 이 작업에 필수적인 Unity ECS 패턴이 포함되어 있습니다.

2. 🔍 문서를 확인한 결과:
   ✅ 사용 가능: [관련 문서 목록]
   ❌ 누락: [필요한 문서 목록]
   
3. 💡 설명을 바탕으로 다음을 추정합니다:
   - 규모: [엔티티 수 추정]
   - 아키텍처: [ECS/MonoBehaviour 권장사항]
   - 일정: [대략적 추정]

함께 자세한 계획을 세우시겠습니까?"
```

#### **요구사항 명확화**
```yaml
반복적 질문:
  1라운드: 고수준 이해
    - "어떤 문제를 해결하고 있나요?"
    - "영향받는 사용자/시스템은 누구인가요?"
    - "성공은 어떻게 보일까요?"
  
  2라운드: 기술적 세부사항
    - "기존 아키텍처에 어떻게 맞나요?"
    - "성능 요구사항은 무엇인가요?"
    - "제약사항이나 한계가 있나요?"
  
  3라운드: 구현 접근법
    - "선호하는 기술적 접근법은?"
    - "[특정 기술적 도전]을 어떻게 처리할까요?"
    - "테스팅 요구사항은 무엇인가요?"
```

### 3.2 계획 문서 생성

#### **작업 계획 생성**
```yaml
생성 출력:
  1. WORK_PLAN_[YYYY-MM-DD].md:
     - 목표 명세서
     - 기술적 접근법

     - 성공 기준

  2. TodoList (TodoWrite 사용):
     - 우선순위가 정해진 작업 목록

     - 의존성 기록

  3. 참조 링크:
     - 관련 문서
     - 코드 예제

```

## 4. 위험 평가 및 완화

### 4.1 위험 범주
```yaml
기술적 위험:
  성능:
    - 위험: 대량 엔티티 수로 인한 프레임레이트 저하
    - 완화: ECS + Job System + LOD 구현
    - 모니터링: 지속적인 프로파일링

  아키텍처:
    - 위험: 기존 시스템 통합 파괴
    - 완화: 인터페이스 기반 설계, 점진적 출시
    - 모니터링: 통합 테스트

  호환성:
    - 위험: Unity 버전 비호환성
    - 완화: 버전 고정, 호환성 테스팅
    - 모니터링: 빌드 검증

프로젝트 위험:
  범위 확장:
    - 위험: 구현 중 요구사항 확대
    - 완화: 명확한 범위 문서화, 변경 통제
    - 모니터링: 정기 범위 검토

  지식 격차:
    - 위험: ECS 패턴 미숙
    - 완화: 문서 학습, 개념 증명
    - 모니터링: 코드 리뷰 체크포인트

  시간 추정:
    - 위험: 복잡성 과소평가
    - 완화: 보수적 추정, 버퍼 시간
    - 모니터링: 30분마다 진행 추적
```

### 4.2 완화 전략
```yaml
예방 조치:
  - 코딩 전 필수 문서 검토
  - 불확실한 접근법에 대한 개념 증명
  - 정기적인 체크포인트 생성
  - 테스팅과 함께하는 점진적 구현

비상 계획:
  - 성능 대안: LOD 시스템 활성화
  - 아키텍처 대안: MonoBehaviour 대안
  - 일정 대안: 범위 축소 옵션
  - 품질 대안: 기술 부채 문서화
```

## 5. 성공 기준 정의

### 5.1 승인 기준 템플릿
```yaml
기능 요구사항:
  - [ ] 명세된 대로 기능 작동
  - [ ] 모든 예외 사례 처리
  - [ ] 에러 처리 구현
  - [ ] 사용자 경험 검증

기술 요구사항:
  - [ ] 성능 목표 달성 (구체적 지표)
  - [ ] 메모리 사용량 제한 내
  - [ ] ECS 패턴 적절히 구현
  - [ ] 통합 테스트 통과

품질 요구사항:
  - [ ] 코드 리뷰 완료
  - [ ] 문서 업데이트
  - [ ] 테스트 커버리지 >80%
  - [ ] 성능 프로파일링
```

### 5.2 완료 정의
```yaml
구현 완료:
  ✅ TodoList의 모든 작업 완료
  ✅ 경고 없이 코드 컴파일
  ✅ 모든 테스트 통과
  ✅ 성능 벤치마크 충족

품질 보증:
  ✅ 코드 리뷰 승인
  ✅ 아키텍처 준수 검증
  ✅ 문서 업데이트
  ✅ 통합 검증

배포 준비:
  ✅ 빌드 검증 통과
  ✅ 성능 회귀 테스트 통과
  ✅ 새로운 기술 부채 발생하지 않음
  ✅ 인수인계 문서 완료
```

## 6. 계획 세션 예시

### 6.1 간단한 작업 계획

**예시 1: 간단한 ECS 컴포넌트 추가**

```
사용자: "인구 수입에 대한 새로운 ECS 컴포넌트를 추가하고 싶습니다"

어시스턴트: "인구 수입 ECS 컴포넌트를 추가하는 것을 도와드리겠습니다. 먼저 문서를 확인해봅시다:

📚 도메인 지식 문서를 검토하셨나요? 이 작업에 필수적인 ECS 컴포넌트 패턴이 포함되어 있습니다.

🔍 문서를 확인한 결과:
   ✅ 사용 가능: DOMAIN_KNOWLEDGE_KOR.md (ECS 패턴 및 성능 가이드라인)
   ✅ 사용 가능: DEVELOPMENT_WORKFLOW_KOR.md (코딩 표준 및 검증)
   ❌ 누락: 인구 경제 시스템 설계 문서

💡 요청을 바탕으로 다음을 포함합니다:
   - 규모: 단일 컴포넌트 생성 (~초기 100개 엔티티)
   - 아키텍처: 순수 ECS 데이터 컴포넌트 (메서드 없음)
   - 일정: ~30분 구현 + 테스팅

이것은 광범위한 계획이 필요하지 않은 간단한 작업입니다. 바로 진행할까요?"

사용자: "네, 진행합시다"

어시스턴트: 다음과 함께 TodoList 생성:
  - PopulationIncomeData 컴포넌트 생성
  - 기존 시스템에 컴포넌트 추가
  - 통합 테스트 업데이트
```

**예시 2: 복잡한 기능 구현**

```
사용자: "완전한 시장 감정 분석 시스템을 구현해야 합니다"

어시스턴트: "이것은 신중한 계획이 필요한 중요한 기능입니다. 상담을 시작해봅시다:

📚 필요한 문서 검토:
   - 도메인 지식 (ECS 패턴): 15분
   - 경제 시스템 아키텍처: 10분  
   - 시장 데이터 설계: 5분

🔍 문서 평가:
   ✅ 사용 가능: DOMAIN_KNOWLEDGE_KOR.md, technical-architecture_KOR.md
   ❌ 누락: 시장 감정 시스템 설계
   ❌ 누락: 데이터 수집 파이프라인 명세
   
💡 다음을 요구하는 복잡한 시스템으로 보입니다:
   - 다중 ECS 시스템 통합
   - 외부 데이터 처리
   - 실시간 분석 기능
   
이것을 제대로 계획하는 데 15-20분을 투자합시다. 먼저, 필요한 감정 분석의 범위는 무엇인가요?

**필수 질문:**
- 이것이 분석할 시장 엔티티는 몇 개인가? (>1000개는 ECS 최적화 필요)
- 감정 분석을 공급할 데이터 소스는?
- 실시간 업데이트가 필요한가, 아니면 주기적 배치 처리?
- 분석 업데이트의 성능 목표는?
- 기존 시장 시스템과 어떻게 통합될까요?"

[요구사항 수집과 함께하는 대화형 계획 세션이 이어집니다]
```

### 6.2 복잡한 계획 세션

**예시: 다중 시스템 통합**

```
사용자: "투자 결정을 위한 완전한 자동화 시스템을 구현하고 싶습니다"

어시스턴트: "이것은 아키텍처의 여러 부분에 영향을 미칠 복잡한 시스템입니다. 체계적으로 계획해봅시다:

## 사전 계획 문서 검토 (15분)
**필수 읽기:**
  📚 도메인 지식: Unity ECS 패턴 및 성능 요구사항

**일정 및 리소스:**
- 선호 일정: 구현에 며칠 또는 몇 주?
```

## 7. 계획 세션 결과물

### 7.1 생성된 문서

**모든 계획 세션에 대해 생성:**

```yaml
작업 계획 문서:
  파일: .claude/doc/workplans/WORK_PLAN_[YYYY-MM-DD]_[기능명].md
  내용:
    - 목표 명세서
    - 기술적 접근법 요약
    - 작업 분해 (에픽/스토리/작업 계층)
    - 성공 기준 및 검증
    - 위험 평가 및 완화
    - 리소스 요구사항
    - 일정 추정

TodoList (TodoWrite):
  작업: 우선순위가 정해진 구현 작업
  상태: pending/in_progress/completed 추적
  의존성: 작업 순서 및 차단 관계
  체크포인트: 진행 검증을 위한 주요 마일스톤

참조 문서:
  링크: 관련 문서 및 코드 예제
  패턴: 따라야 할 아키텍처 패턴
  벤치마크: 성능 및 품질 목표
  검증: 테스팅 및 승인 기준
```

### 7.2 세션 인계 프로토콜

```yaml
세션 체크포인트 생성:
  트리거: 2시간 작업마다 또는 세션 중단 전
  내용:
    - 현재 작업 상태 및 완성도 백분율
    - 생성된 작업 산출물 (파일, 테스트, 문서)
    - 알려진 이슈 및 차단 의존성
    - 다음 단계 및 우선순위 순서
    - 세션 재개를 위한 컨텍스트 보존

세션 재개 프로토콜:
  검토: 이전 체크포인트 및 작업 계획 상태
  검증: 현재 상태가 체크포인트와 일치하는지 확인
  계획: 요구사항이나 제약사항의 변경사항 평가
  실행: 문서화된 다음 단계부터 계속
```

## 8. 품질 보증

### 8.1 계획 품질 게이트

```yaml
계획 완전성 확인:

  - [ ] 아키텍처에 대해 기술적 접근법 검증됨
  - [ ] 모든 의존성이 식별되고 가용성 확인됨
  - [ ] 성능 요구사항이 명시되고 실현 가능함
  - [ ] 완화 전략과 함께 위험 평가 완료
  - [ ] 리소스 요구사항이 추정되고 사용 가능함
  - [ ] 복잡성 평가에 기반한 현실적인 일정
  - [ ] 승인 기준과 함께 테스팅 전략 정의됨

문서 품질 확인:
  - [ ] 작업 계획 문서가 생성되고 접근 가능함
  - [ ] TodoList가 의존성과 함께 적절히 구조화됨
  - [ ] 참조 문서가 링크되고 최신임
  - [ ] 성공 기준이 측정 가능하고 테스트 가능함
  - [ ] 위험 완화 전략이 실행 가능함
```

### 8.2 지속적인 계획 검증

```yaml
일일 검증 (다일 작업인 경우):

  - 필요한 요구사항 변경 또는 명확화
  - 리소스 가용성 및 일정 조정

주간 계획 검토 (다주 작업인 경우):
  - 진화하는 요구사항과 목표 정렬  
  - 아키텍처 결정 검증
  - 성능 목표 진행 상황
  - 위험 현실화 및 완화 효과
```
