# 작업 세션 추적기

[🇬🇧 English Version](./WORK_SESSION_TRACKER.md)

## 📍 네비게이션

[↩️ 레퍼런스로 돌아가기](./INDEX_KOR.md) | [📚 문서 인덱스](../INDEX_KOR.md) | [🏠 홈](../../../CLAUDE_KOR.md)

## 🎯 목적

**포괄적인 세션 관리 시스템**으로 여러 Claude Code 세션 간 작업 연속성을 유지하여 전체 컨텍스트 보존과 함께 매끄러운 작업 중단 및 재개를 가능하게 합니다.

## 1. 세션 아키텍처

### 1.1 세션 유형

```yaml
세션 분류:
  단일 작업 세션:
    기간: 30분 - 2시간
    범위: 단일 기능/수정 완성
    추적: 기본 TodoList + 최종 요약
    예시: "인구 수입용 ECS 컴포넌트 추가"

  다중 작업 세션:
    기간: 2-8시간
    범위: 여러 관련 작업/기능
    추적: 2시간마다 상세 체크포인트
    예시: "완전한 투자 자동화 시스템 구현"

  프로젝트 세션:
    기간: 며칠/몇 주
    범위: 에픽 레벨 기능 개발
    추적: 일일 요약 + 주간 계획 업데이트
    예시: "경제 시뮬레이션 전면 개편"

  조사 세션:
    기간: 가변적 (30분 - 4시간)
    범위: 문제 분석, 아키텍처 연구
    추적: 증거 수집 + 발견사항 문서화
    예시: "시장 시스템의 성능 병목 조사"
```

### 1.2 컨텍스트 계층

```yaml
컨텍스트 보존 계층:
  레벨 1 - 즉시 (TodoList):
    범위: 현재 세션 작업 및 진행 상황
    지속성: 세션 생명주기
    복구: TodoRead를 통한 자동
    사용: 활성 작업 추적

  레벨 2 - 세션 (작업 계획):
    범위: 완전한 작업 목표 및 접근법
    지속성: 세션 간 지속 (workplans/에 저장)
    복구: 세션 시작 시 수동 참조
    사용: 컨텍스트 복원 및 범위 검증

  레벨 3 - 프로젝트 (문서):
    범위: 아키텍처, 패턴, 도메인 지식
    지속성: 영구적 (버전 제어됨)
    복구: 계획 프로토콜을 통한 자동
    사용: 기술 컨텍스트 및 제약사항
```

## 2. 세션 생명주기 관리

### 2.1 세션 초기화

#### **새 세션 시작 프로토콜**
```yaml
1단계: 컨텍스트 평가 (2-3분)
  질문:
    - 이전 작업을 계속하는 것인가?
    - 기존 작업 계획이 있는가?
    - 어떤 문서 컨텍스트가 필요한가?
  
  행동:
    - .claude/doc/workplans/에서 기존 작업 계획 확인
    - 관련 도메인 문서 검토
    - git status를 통한 현재 프로젝트 상태 평가

2단계: 작업 계획 활성화 (1-2분)
  새 작업:
    - WORK_PLANNING_PROTOCOL_KOR.md 따르기
    - 새 작업 계획 문서 생성
    - 계획 결과로 TodoList 초기화
  
  계속되는 작업:
    - 기존 작업 계획 로드
    - 이전 세션 체크포인트 검토
    - 마지막 알려진 상태에서 TodoList 업데이트

3단계: 세션 설정 (1분)
  설정:
    - 세션 기간 추정
    - 체크포인트 간격 설정 (기본: 2시간)
    - 복잡성에 따른 추적 레벨 설정
    - 세션 성공 기준 설정
```

#### **세션 복원 프로세스**
```yaml
복원 체크리스트:
  - [ ] 이전 세션 요약을 찾고 검토
  - [ ] 작업 계획 문서가 최신이고 접근 가능
  - [ ] TodoList를 마지막 알려진 상태로 복원
  - [ ] 마지막 세션 이후 코드 변경사항 식별
  - [ ] 이전 세션의 차단 이슈 해결
  - [ ] 세션 목표 및 우선순위 명확화
  - [ ] 테스팅 환경 검증 및 준비 완료
```

### 2.2 활성 세션 관리

#### **지속적인 추적 요소**
```yaml
실시간 업데이트:
  TodoList 관리:
    빈도: 각 작업 완료 후
    내용: 작업 상태, 완료 증거, 다음 행동
    품질 게이트: 항상 단일 in_progress 작업 보장
  
  진행 상황 문서화:
    빈도: 복잡한 작업은 30분마다
    내용: 코드 변경, 내린 결정, 직면한 장애물
    형식: 커밋 메시지, 인라인 주석, 결정 로그
  
  컨텍스트 보존:
    빈도: 컨텍스트나 도구 전환 전
    내용: 현재 집중점, 논리, 다음 의도된 행동
    저장: 내부 세션 메모리 + 외부 문서
```

#### **체크포인트 생성 전략**
```yaml
자동 체크포인트:
  시간 기반:
    트리거: 활성 작업 2시간마다
    내용: 전체 컨텍스트 스냅샷 + 진행 평가
    
  작업 기반:
    트리거: 주요 작업 완료나 중요한 마일스톤
    내용: 성취 요약 + 다음 단계 계획
    
  컨텍스트 전환:
    트리거: 작업 집중점 변경이나 주요 컴포넌트 간 전환
    내용: 컨텍스트 경계 + 인계 정보

수동 체크포인트:
  비상 중단:
    트리거: 예상치 못한 세션 종료 필요
    내용: 현재 상태 + 중요한 계속 정보
    
  결정 지점:
    트리거: 주요 아키텍처나 구현 결정
    내용: 결정 근거 + 고려된 대안
    
  검증 지점:
    트리거: 테스팅 완료나 품질 검증
    내용: 결과 요약 + 품질 평가
```

### 2.3 세션 종료

#### **계획된 세션 종료 프로토콜**
```yaml
종료 전 체크리스트 (5-10분):
  코드 상태:
    - [ ] 모든 변경사항이 설명적인 메시지와 함께 커밋됨
    - [ ] 불안정한 상태의 작업 중 파일이 남아있지 않음
    - [ ] 완료된 작업에 대해 테스트 실행 및 통과
    - [ ] 빌드 검증 성공적으로 완료

  문서 상태:
    - [ ] TodoList가 현재의 정확한 상태로 업데이트됨
    - [ ] 계속 컨텍스트와 함께 세션 체크포인트 생성
    - [ ] 진행 상황 및 발견사항으로 작업 계획 업데이트
    - [ ] 새로운 결정이나 발견사항 문서화

  계속 계획:
    - [ ] 다음 세션 우선순위 식별 및 문서화
    - [ ] 차단 이슈 에스컬레이션 또는 해결
    - [ ] 계속을 위한 리소스 요구사항 평가
    - [ ] 쉬운 복원을 위한 세션 인계 요약 생성
```

#### **비상 종료 프로토콜**
```yaml
신속한 컨텍스트 보존 (<2분):
  중요한 정보:
    - 현재 작업 상태 및 완료 백분율
    - 사용 중이던 마지막 작업 접근법/방법
    - 계획되었던 즉시 다음 단계
    - 직면한 차단 이슈나 에러 상태
  
  빠른 문서화:
    - 현재 실상으로 TodoList 업데이트
    - 세션 로그에 비상 체크포인트 생성
    - "WIP:" 접두사로 가치 있는 작업 커밋
    - 중요한 결정이나 발견사항 기록
```

## 3. 세션 문서화 표준

### 3.1 세션 로그 템플릿

```yaml
SESSION_LOG_[YYYY-MM-DD]_[session-id].md:
  
  메타데이터:
    session_id: 고유 식별자
    start_time: 세션 시작 타임스탬프
    end_time: 세션 완료 타임스탬프
    duration: 총 활성 작업 시간
    session_type: single-task|multi-task|project|investigation
    
  컨텍스트:
    work_plan: 활성 작업 계획 문서 참조
    previous_session: 마지막 관련 세션으로의 링크
    todo_list_state: 세션 시작 시 TodoList
    
  진행상황:
    achievements: 세션 중 주요 성취
    code_changes: 수정된 파일, 변경된 라인, 추가된 기능
    decisions_made: 중요한 기술/아키텍처 결정
    obstacles_encountered: 직면한 문제 및 해결 상태
    
  계속:
    next_priorities: 다음 세션을 위한 상위 3 우선순위
    blocking_issues: 주의가 필요한 미해결 문제
    context_notes: 세션 재개를 위한 중요한 컨텍스트
    estimated_remaining: 작업 완료를 위한 시간/노력 추정
```

### 3.2 체크포인트 문서화

```yaml
CHECKPOINT_[timestamp].md:
  
  현재 상태:
    active_task: 작업 중인 현재 TodoList 작업
    completion_percentage: 활성 작업의 완료 추정치
    last_working_approach: 현재 사용 중인 방법/전략
    
  기술 컨텍스트:
    code_location: 수정 중인 특정 파일/함수
    test_state: 현재 테스팅 상태 및 결과
    build_state: 컴파일 및 빌드 검증 상태
    performance_state: 발견된 성능 영향
    
  결정 흔적:
    recent_decisions: 이 세션에서 내린 기술적 선택
    alternatives_considered: 평가된 옵션들
    rationale: 선택의 근거
    
  미래 계획:
    immediate_next_steps: 계획된 다음 2-3개의 구체적 행동
    session_goals: 현재 세션의 남은 목표
    risk_assessment: 앞으로의 잠재적 이슈나 합병증
```

## 4. 컨텍스트 보존 전략

### 4.1 기술 컨텍스트 보존

```yaml
코드 컨텍스트:
  변경 추적:
    방법: 30-60분마다 설명적인 git 커밋
    내용: 변경의 의도, 접근법, 논리
    품질: 각 커밋은 자체 설명적이어야 함
  
  상태 문서화:
    방법: 복잡한 로직을 위한 인라인 주석
    내용: 설계 결정, 성능 고려사항, 예외 사례
    품질: 주석은 "무엇"이 아닌 "왜"를 설명해야 함
  
  아키텍처 컨텍스트:
    방법: 관련 아키텍처 문서 업데이트
    내용: 새로운 패턴, 통합, 설계 결정
    품질: 문서를 구현과 함께 최신으로 유지

개발 환경:
  도구 상태:
    IDE 설정: 사용된 특별한 설정이나 확장 문서화
    Unity 설정: 프로젝트 설정이나 패키지 변경사항 기록
    테스팅 환경: 테스트 데이터, 설정, 특별한 설정 문서화
  
  성능 컨텍스트:
    프로파일링 데이터: 성능 측정 및 분석 저장
    벤치마크: 기준 성능 및 개선 목표 문서화
    메모리 사용: 메모리 할당 패턴 및 최적화 기회 추적
```

### 4.2 지식 컨텍스트 보존

```yaml
도메인 지식:
  비즈니스 로직:
    방법: 새로운 통찰로 게임 디자인 문서 업데이트
    내용: 게임 메카닉, 경제 모델, 플레이어 행동 패턴
    트리거: 구현 중 게임플레이 영향 발견 시
  
  기술적 통찰:
    방법: 기술 결정 로그 유지
    내용: ECS 패턴, 성능 기법, Unity 특정 접근법
    트리거: 새 기법 학습이나 복잡한 문제 해결 시
  
  문제-해결 패턴:
    방법: 반복되는 문제와 효과적인 해결법 문서화
    내용: 일반적인 버그, 성능 병목, 통합 도전
    트리거: 이전에 해결된 문제 재발견 시

학습 진행:
  기술 개발:
    방법: Unity ECS, 성능 최적화에서의 진행 추적
    내용: 학습된 새 기법, 숙련도 개선
    목적: 경험에 따른 미래 작업 접근법 최적화
  
  도메인 전문성:
    방법: 경제 시뮬레이션 패턴의 지식 베이스 구축
    내용: 수학적 모델, 알고리즘 접근법, 데이터 구조
    목적: 시간이 지남에 따라 결정 속도와 품질 향상
```

### 4.3 협력 컨텍스트

```yaml
소통 상태:
  결정 근거:
    방법: 특정 접근법을 선택한 이유 문서화
    내용: 고려된 트레이드오프, 이해관계자 입력, 제약 요인
    목적: 미래 개발자가 결정을 이해하고 수정할 수 있도록
  
  사용자 요구사항:
    방법: 요구사항에서 구현까지의 추적성 유지
    내용: 원래 사용자 필요, 해석 결정, 구현 선택
    목적: 사용자 의도에 대해 구현 검증
  
  품질 표준:
    방법: 품질 게이트 및 검증 기준 문서화
    내용: 성능 목표, 코드 품질 지표, 테스팅 표준
    목적: 세션 경계 간 일관된 품질 유지
```

## 5. 세션 분석 및 최적화

### 5.1 세션 효과성 지표

```yaml
생산성 지표:
  작업 완료율:
    계산: (완료된 작업 / 계획된 작업) * 100
    목표: 계획된 작업에 대해 >85% 완료율
    분석: 계획 정확성 및 실행 효율성 식별
  
  컨텍스트 전환 오버헤드:
```

## 🎯 세션 성공 기준

**세션 관리 효과성:**
- ✅ **<5분 컨텍스트 복원**: 체크포인트에서 완전한 작업 컨텍스트 복원 시간
- ✅ **>85% 작업 완료율**: 성공적으로 완료된 계획 작업의 백분율
- ✅ **제로 컨텍스트 손실 사고**: 부적절한 세션 관리로 인한 작업 손실 없음
- ✅ **±20% 추정 정확성**: 허용 범위 내의 세션 기간 및 범위 추정

**품질 유지:**
- ✅ **아키텍처 일관성**: 세션 경계 간 코드 품질 저하 없음
- ✅ **문서 최신성**: 모든 문서가 최신이고 정확한 상태 유지
- ✅ **성능 안정성**: 세션 중단으로 인한 성능 회귀 없음

**생산성 최적화:**
- ✅ **<10% 오버헤드**: 총 세션 시간의 10% 미만인 컨텍스트 관리 오버헤드
- ✅ **매끄러운 계속**: 10분 내에 완전한 생산성으로 작업 재개 능력
- ✅ **지식 보존**: 세션 간 기술 통찰 및 결정 보존
